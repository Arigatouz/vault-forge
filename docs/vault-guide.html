1. The mental model

Three layers, built in order. Each one is a plain file you can read without any tooling.

Structure

Folders, note templates, Obsidian config, theme. Written once by init. Answers: where does this note belong?

Content

Notes. scan writes the skeleton notes from the repository's metadata. ingest writes real notes from the repository's documents and source code. Answers: what is in this repository?

Retrieval

index turns every note into heading-level chunks with line ranges, and search ranks them. Answers: which note covers this, and where?

The gate

validate re-reads the vault and fails on a broken link, a missing property, a bad canvas reference or a stale index. Nothing is "done" until it prints PASS.

2. The five commands

CommandReadsWrites
initThe template tree shipped with the tool. docs-vault/ skeleton, .obsidian config, Templates/, the vault README.md, and a vendored copy of the tool into .vault-forge/.
scanManifests (package.json, Cargo.toml, *.sln, *.csproj), README.md, Makefile, the git log, the file tree, docs/ names. The project note, one MOC per area, Codebase Map, Repo Conventions, the inbox, today's daily note, the vault canvas.
ingestEvery document in docs/ and the repository root, plus every source file (grouped per module). One note per document with its section headings and source line ranges, one outline note per module listing declarations with file:line, and the two maps Repo Docs and Code Outline.
indexEvery note in the vault (templates excluded). index/vault-index.json, index/chunks.jsonl, index/index.md.
validateThe whole vault plus the index. Nothing. It prints a per-check table and exits 1 when anything is wrong.

build runs init (only if the vault is missing), scan, ingest, index, validate. Add --skip-ingest for the fast metadata-only path. status prints what the current repo has.

cd <repo>
npx -y github:Arigatouz/vault-forge#v0.3.0 init --name "My App"   # once per repository
./.vault-forge/vault-forge build                                 # after that, the vendored copy
./.vault-forge/vault-forge search "where is auth handled"        # the agent fast path
Pin the tag, and know that npx caches. A plain npx -y github:Arigatouz/vault-forge can silently re-run an older cached copy after the tool changes. Pin #v0.3.0, and add --prefer-online when you want to be sure you have the newest. The vendored copy inside the repo is the one your team should run: it is the version the repo pinned.

4. Frontmatter schema

Every note starts with YAML properties. They are not decoration: the dashboards are Bases views that filter on them, so a missing property means a note that silently disappears from the dashboard.

---
type: note            # note | moc | project | area | resource | content | daily | meeting | decision
status: active        # inbox | idea | draft | active | paused | done | published | archived | logged
area: "[[Architecture]]"   # the area MOC this belongs to; omit on the area note itself
tags: [concept]       # lowercase, from the vocabulary in the vault README
created: 2026-10-12   # date only, YYYY-MM-DD
updated: 2026-10-12   # bump on every substantive edit
priority: medium      # high | medium | low
---
TypeExtra properties it may carry
projectnext_action, due, repo
contentcontent_type, stage, audience, publish_date, channel
resourcesource, source_url, confidence, review_date, publishable
decisiondecision_date; superseded decisions get status: archived
dailyNothing extra: the filename date is the identity
Why the vocabularies matter. validate fails a note whose type or status is outside the list, and a Bases filter that expects status == "active" will not match status: ongoing. If you need a new value, add it to the vault README first, then use it.

6. Anatomy of a note

# Architecture                 # the H1 is the note's visible title

One or two sentences that say what this is.

## Contents                    # structured body: headings, lists, tables

- [[AI Tutor Platform]]
- [[Backend]]

## Related                     # the links that actually matter, 2 to 4 of them

- [[Home]]
- [[Codebase Map]]
  • Wikilinks only for internal links: [[Note Name]] or [[Note Name|display text]]. Markdown links are for external URLs.
  • Basenames must be unique across the vault. That is what makes [[Dashboard]] resolve from anywhere without a path. Two notes called Overview break that promise; one wins and the other becomes unreachable.
  • Link laterally. A note links to the two or three notes it truly depends on. Linking everything back to a hub flattens the graph into a star.
  • Assets link with their extension: [[Vault Overview.canvas|Vault Overview]], ![[Projects.base#Active]].

7. Dashboards and Bases

05-Dashboards/Dashboard.md embeds four Bases views. A .base file is a saved query: filters, formulas, properties and named views. Nothing in it is hand-maintained data; it reads your notes' properties.

BaseFilters onViews
Projects.basetype == "project", not archived, not templates Active, All projects, By area
Content Pipeline.basetype == "content"Pipeline
Resource Library.basetype == "resource"By confidence
Daily Log.basetype == "daily"Recent

Embed one view with ![[Projects.base#Active]]. Add a view by editing the .base file: add an entry under views: with a type (table or cards), a name and an order list.

If a dashboard looks empty it is almost always the properties, not the Base: a note missing type, or carrying a status the view does not expect, simply does not appear. Run validate first: it reports missing properties by file name.

8. Canvas boards

06-Canvases/Vault Overview.canvas is a JSON Canvas file: nodes with type: file (pointing at a note) or type: text, plus edges with fromNode and toNode. Open it in Obsidian to drag cards around; the file is diffable, so a canvas change is reviewable like any other file.

validate parses every canvas and fails if a node id repeats, an edge points at a node that does not exist, or a file node points at a note that is missing on disk.

9. Graph view

.obsidian/graph.json pre-seeds colour groups. Order matters: the first matching query wins, so tags are listed before paths.

QueryGroup
tag:#decision, tag:#concept, tag:#reference, tag:#moc, tag:#archiveBy note kind, so kind beats location
path:"01-Projects" … path:"07-Daily"By folder, for everything untagged
path:"09-Attachments"Faint, so it stays out of the way
The graph groups can vanish. A running Obsidian rewrites graph.json whenever its own settings change, and it will overwrite what the tool wrote. If the colours disappear: close the app, re-run init --force for that one file, or re-add the groups by hand from the vault README. Same rule for appearance.json.

10. The search index

Three files under index/, regenerated by index:

FileWhat is in it
vault-index.jsonOne record per note: title, type, status, tags, headings with line numbers, outbound links, word count, and the commit it was built from.
chunks.jsonlOne JSON object per heading: the heading, its level, the line range, and the text of that section. This is what makes path:line citations possible without reading whole files.
index.mdA human catalog: every note grouped by folder with one line of summary.
./.vault-forge/vault-forge search "tutor escalation policy" --limit 3
01-Projects/AI Tutor Platform.md                 :13  [27.8 4/4]  Company Academy
    An internal learning platform with a Socratic AI tutor …

./.vault-forge/vault-forge search "keycloak" --json     # what an agent consumes
[{ "score": 9.25, "terms_matched": "1/1", "path": "…", "line": 17, "heading": "…", "text": "…" }]
  • [score matched/total] tells you whether a hit matched every word you typed. A 1/3 hit is a partial match: useful, but do not treat it as an answer.
  • Filters: --tag tauri, --kind decision. Bump --limit for more hits.
  • Rebuild after a batch of edits: index. validate warns when the index is older than the newest note.
  • Honest limit: this is literal term scoring with boosts for title, heading, path and full-phrase matches. It is not semantic search. It is instant, free, offline, and it cites a line number.

11. The Agent Dispatch add-on

A local Obsidian plugin that fires a prompt at a coding-agent CLI, picks the model, streams the answer into a panel, and logs the run. Four agents are wired: Codex, Claude Code, Antigravity, OpenCode.

Installing it, and proving it runs

./.vault-forge/vault-forge plugin install --from-github Arigatouz/agent-dispatch   # or @v0.1.0 to pin
./.vault-forge/vault-forge plugin status    # files, registry entry, and when it last started
./.vault-forge/vault-forge plugin doctor    # exit 0 only when it has really started in this vault

doctor is the honest check, because installing is not the same as running. The files can be on disk and the id can be listed in community-plugins.json while Obsidian still treats this vault as not allowing plugins, in which case there is no ribbon icon and no command, and nothing in the plugin's own logs will say so. doctor reads the heartbeat file the plugin writes when it loads (LOADED.txt, next to main.js) and fails with the exact two clicks when it is missing. validate raises the same condition as a warning, so build surfaces it unasked.

Where it lives in the UI

To do thisDo this
Open the run panelClick the terminal icon in the left ribbon, or Cmd/Ctrl+P → Agent Dispatch: Open the run panel.
Send a promptPress FIRE in the panel, or the command Fire request at an agent.
Send the text you selected in a noteCommand Send the selection to an agent; the answer can be inserted under the selection.
Kill a runaway runCancel all in the panel header, or the command Cancel every live run.
Move the panel to the right sidebarRight-click the panel tab → Move to right sidebar. That is how it was designed to sit.

The fire modal

  1. Agent: codex, claude, agy, opencode.
  2. Model: the list is per agent and editable in settings. The requested model is recorded separately from the model the CLI reports.
  3. Prompt: Enter fires, Shift+Enter adds a line.

Each run card shows the agent, the requested model, the CLI-reported model when the CLI prints one, the status (queued, running, done, error, timeout, cancelled), and the elapsed time, with buttons to cancel, insert the answer, save it as a note in 00-Inbox/, or copy it.

Safety posture, per agent

AgentMechanismWhat protects the run
CodexOS sandbox-s read-only in argv
Claude CodeTool permissions--permission-mode plan
AntigravityTool permissions--mode plan --sandbox
OpenCodeNone availableNothing; the panel says UNRESTRICTED instead of pretending otherwise

The prompt is passed as one argument with no shell, so a prompt can never become a command. Run logs go to .obsidian/plugins/agent-dispatch/runs/, which Obsidian does not index, so they never pollute the vault's search or its graph. Binary paths are resolved per machine: the settings value first, then ~/.local/bin, Homebrew, /usr/local/bin, then PATH.

If the panel is missing, ask the app rather than the files. Community plugins can be off for one vault while on for another, and that is per vault, not global. Open Settings → Community plugins: if you see the Restricted-mode notice, the plugins are off here. Turn it on, enable Agent Dispatch, and confirm the plugin started by looking for LOADED.txt next to its main.js. A folder on disk and an entry in community-plugins.json are necessary but not sufficient: Obsidian loads only what it considers enabled at launch.

12. Git rules

CommittedIgnored (per-user state)
Everything in docs-vault/: notes, templates, bases, canvases, .obsidian app config, snippets, the index, and .obsidian/plugins/agent-dispatch/ .obsidian/workspace.json, .obsidian/cache, plugin data.json, .trash/
  • The vault lives next to the code on purpose: a note that claims a behaviour change lands in the same commit as the change.
  • A CI step can run ./.vault-forge/vault-forge validate verbatim; it exits non-zero on a broken link, a missing property, a bad canvas reference or a stale index.
  • Set "commit_index": false in .vault-forge/forge.json if you would rather each machine built its own index.

13. Daily workflow

  1. Capture into 00-Inbox/ the moment something is worth keeping. Do not file it yet.
  2. File it later: move it to the project or area it belongs to, set type, area and tags, remove #inbox.
  3. Write from the template that matches, so the properties are right by construction.
  4. Link it to two or three notes it depends on and add it to the area MOC's list.
  5. After a batch of edits: ./.vault-forge/vault-forge index && ./.vault-forge/vault-forge validate.
  6. Once a week: open the Dashboard, look at what is stalled, and pull up the daily notes from 07-Daily/.
  7. When the repository moves on: re-run ingest for the changed docs and modules, then index. Hand-written notes are never overwritten by ingest unless you pass --force.

15. What the generator does not do

  • It does not summarise with a model. ingest is deterministic: section headings, the opening lines of each section, declarations with line numbers. Nothing is invented, and nothing leaves the machine.
  • Section text is trimmed (about 420 characters per section) and long modules list a capped number of files and declarations, with the cap stated in the note. The full text is always in the source file at the cited line.
  • Generated code is skipped: build output, migrations' designer files, node_modules, bin/, obj/.
  • Hand-written notes are never overwritten by a re-run, unless you pass --force, and that flag is scoped to the notes the pass generates.
  • The index is literal, not semantic. If you need meaning-based retrieval, that is a different component with a different cost profile.
